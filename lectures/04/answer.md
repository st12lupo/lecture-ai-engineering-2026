- 取り組んだレベル：発展
- やったこと：
  SWE-bench Verified を選び、Hugging Face の Dataset Viewer で難易度ラベルの違う問題を 5 件読んだ。作成と検証の人数・手順・採点の方法を論文と OpenAI のブログで調べ、今日の評価セットと比べた。
  - データセット：SWE-bench Verified（test 500 件）https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified
  - 元の論文：C. E. Jimenez et al.「SWE-bench: Can Language Models Resolve Real-World GitHub Issues?」（ICLR 2024）https://arxiv.org/abs/2310.06770
  - Verified の作成：OpenAI「Introducing SWE-bench Verified」（2024/8/13）https://openai.com/index/introducing-swe-bench-verified/
  - その後の監査：OpenAI「Why we no longer evaluate SWE-bench Verified」（2026/2/23）https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/
- 結果：
  - 1 件の形式：実際の GitHub の issue の本文（問題文）と、修正前のリポジトリが渡され、issue を直すパッチを出す。採点に使うテストはモデルに見せない
  - 読んだ問題（要約。カッコ内は難易度ラベル、採点テストの数 FAIL_TO_PASS / PASS_TO_PASS、正解パッチの規模）
    1. `django__django-11099`（15 分未満、3 / 19、1 ファイル 2 行の置換）：ユーザー名を検証する正規表現の末尾が `$` なので、末尾に改行が付いた名前が通ってしまう。issue に直し方（`\A`〜`\Z` を使う）まで書いてある。自分でも解ける。LLM にも易しいが、OpenAI の監査では Gemini 3 Flash がタスク ID だけから問題文と正解パッチをほぼ逐語で出しており、「解けた」のか「覚えていた」のかを区別できない
    2. `sympy__sympy-19637`（15 分未満、1 / 40、1 ファイル +3/-1）：`kernS("(2*x)/(x-1)")` が UnboundLocalError（変数 `kern` が代入前に参照される）で落ちる。問題文は再現コードとエラーだけ。エラーから「`kern` が一部の条件でしか代入されない」と推測できるので、該当の関数を読めば自分でも解けそう。LLM もコードの場所を探せれば易しい
    3. `astropy__astropy-12907`（15 分〜1 時間、2 / 13、1 ファイル 1 行）：複合モデルを入れ子にすると `separability_matrix` の結果が変わり、本来は独立な入出力が独立でないと出る。期待する出力が具体的に書いてあるので「何が正しいか」は明確。ただ、直すのは行列を組み立てる内部関数 `_cstack` の 1 行（右側のブロックを 1 で埋めていたのを、右側のモデルの行列そのものにする）で、ライブラリの仕組みを理解しないと見つけにくく、自分はすぐには解けない。LLM は、再現して行列を追えれば解けそう
    4. `sphinx-doc__sphinx-7590`（4 時間超、1 / 24、3 ファイル +89/-18）：Sphinx の C++ ドメインが、`6.62607015e-34q_J` のようなユーザー定義リテラルを解析できず警告を出す。「対応してほしい」という機能追加の依頼で、C++ の文法と Sphinx 独自のパーサーの両方を理解する必要がある。自分には解けない。元の PR のテストは、解析結果から作られる内部の ID（マングリングされた名前）を文字列で照合しているので、LLM は動く実装を作るだけでなく、テストが期待する内部表現に合わせる必要がある
    5. `pydata__xarray-6992`（4 時間超、12 / 945、2 ファイル +85/-38）：インデックスの作り直しの後、座標名の数が変数の数より多くなる状態が生まれ、表示などが壊れる。期待するふるまいは「この前提はもう正しくないようだ」程度で、どこをどう直すかは書かれていない。自分には解けない。LLM は、直す場所を自分で決めたうえで、945 件の既存テストを壊さない必要がある
  - 難易度の分布（Dataset Viewer で difficulty 列を数えた）：15 分未満 194 件、15 分〜1 時間 261 件、1〜4 時間 42 件、4 時間超 3 件。9 割以上が 1 時間未満の課題（ブログの「easy 196 件」とは 2 件ずれていた）

  - 採点の方法：LLM 採点ではなく、テストの実行。モデルのパッチを当てて、FAIL_TO_PASS（issue が直ったかを見るテスト）と PASS_TO_PASS（既存の機能を壊していないかを見るテスト）がすべて通れば解決とする。指標は解決した割合（% Resolved）

- 気づき・疑問：
  - Verified が問題を除外した理由「問題文が曖昧で、テストが特定の解釈しか認めない」は、演習の rubric.md の「まだ決めていないこと」と同じ構造だと感じた。基準（テスト）が決めていない論点があると、正しい回答が不合格になったり、判定が割れたりする。決められない問題を自動判定から外す点も共通している（Verified は 3 人のうち 1 人でも問題ありとすれば除外、演習は unsure にして人が見る）
  - コードで判定する（テストを実行する）と客観的に見えるが、それでも採点器の側が間違う。「狭すぎるテスト」は演習の過検出（LLM=fail・自分=pass）に当たる。講義資料で紹介された METR の結果（テストに通った修正の約半分はメンテナーが取り込まない）は、見逃し（LLM=pass・自分=fail）に当たる。採点器がコードでも LLM でも、人の判断と照らして確かめる必要があるのは同じだと分かった
  - 93 人が 3 人ずつ 1,699 件を見て、後から 6 人以上で監査しても、138 件中 6 割に不備が残っていた。10 件を 1 人で作った今日の評価セットに誤りがない保証はないので、不合格を見たら、正解（期待するふるまい・rubric.md）の側も疑う必要がある
  - 読んだ 5 件のうち、15 分未満の 2 件は issue に原因や直し方がほぼ書いてあった。4 時間超の 2 件は、「何が正しいか」から自分で決める必要があった。難しさはコードの量よりも、問題文がどこまで決めているかで決まるように思えた
  - 疑問：演習の評価セットと講師のラベルも、講座の公開 repo に置いてある。将来のモデルがこれを学習すると、同じ混入が起こりうる。自分のアプリの評価セットでは、講義の「調整用と確認用に分ける」に加えて、確認用は公開しない運用まで必要なのか
